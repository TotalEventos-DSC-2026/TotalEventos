# Artefato 07 — Plano de atualização do GitHub

## 1. Objetivo

Orientar a equipe na atualização do repositório GitHub para refletir a governança, os assignees, os revisores e a prontidão das issues.

## 2. Checklist operacional

### 2.1 Conferência de integridade
- Verificar a existência da Epic e das Sub-Issues no repositório.
- Confirmar nomes, títulos e descrições originais.
- Validar que os identificadores e a rastreabilidade foram preservados.

### 2.2 Atualização de assignees
- Atribuir responsável técnico para cada Sub-Issue.
- Registrar um líder de área para blocos críticos como `SUB-03` e `SUB-05`.
- Manter a atribuição consistente com a matriz da etapa anterior.

### 2.3 Registro de revisores
- Designar revisores diferentes dos assignees.
- Confirmar que cada atividade tem revisão cruzada independente.
- Registrar quem validará critérios de aceite e DoR.

### 2.4 Publicação dos comentários de revisão
- Inserir os comentários técnicos previstos no Artefato 05 em cada issue.
- Manter linguagem orientada à ação e critérios de prontidão.
- Registrar elementos do planejamento que necessitam de ajuste.

### 2.5 Ajustes de descrição
- Corrigir descrições de transação, critérios de aceite e dependências.
- Garantir que os textos reflitam a análise de revisão cruzada.
- Atualizar o status de cada issue conforme a revisão.

### 2.6 Governança do board
- Utilizar apenas os 5 estados do fluxo: `Backlog`, `Ready`, `In Progress`, `In Review`, `Done`.
- Manter em `Backlog` qualquer issue que não concluiu os 7 critérios do DoR.
- Promoção para `Ready` só ocorre após revisão humana e critérios vigentes.
- Não criar labels de status no repositório.

### 2.7 Auditoria final do board
- Verificar se todas as issues aparecem no board correto.
- Revisar consistência das colunas.
- Confirmar presença de pendências e próximos passos.

## 3. Recomendação de atuação

- O coordenador deve validar a atualização dos assignees e dos estados.
- O responsável técnico deve validar o alinhamento do escopo e da revisão.
- O revisor precisa registrar a revisão formal e indicar se a issue pode ser promovida.

## 4. Conclusão

Este plano deve ser implementado no GitHub somente após a equipe confirmar seus dados reais e os responsáveis por cada issue. Até esse momento, a documentação local deve ser mantida como base de governança e revisão técnica.
